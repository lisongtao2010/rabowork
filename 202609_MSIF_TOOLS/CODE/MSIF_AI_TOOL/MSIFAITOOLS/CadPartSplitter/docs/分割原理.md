# CadPartSplitter 分割原理说明

> 本文说明 `CadPartSplitter` 把一张工程图纸自动切成若干张零件图的**完整技术原理**：
> 每一步做什么、为什么这么做、参数在哪个环节起作用、失败时应该调什么。
> 文中提到的代码位置（`PartDetector.cs` 等）均指上一级目录（项目根目录）中的同名文件。

---

## 1. 要解决的问题

输入是一张典型的机械装配图纸（A1 / A2，CAD 导出的矢量 PDF，或同版式的扫描图）：

```
┌──────────────────────────────────────────────────────────────┐
│ ┌─ 零件视图 A（细长杆，竖放）  ┌─ 零件视图 B（剖视，横放）      │
│ │                              │                              │
│ │   尺寸标注 / 引出线 / 编号     │   剖面线 / 文字 / 符号         │  部品表
│ │                              │                              │  タイプ表
│ └─                             └─                             │  詳細表
│ ┌─ 零件视图 C（与 A 同名，镜像）  ┌─ 零件视图 D（…）             │  表題欄
│ └─                             └─                             │
│  注）1. □□ 内は別梱包を示す。 2. …（底部注记文字）              │
└──────────────────────────────────────────────────────────────┘
```

目标：**找出每一个零件视图的矩形范围，各自裁成一张 PNG**，供后续 CAD 识别 / 报价流程使用；
右侧的部品表 / タイプ表 / 表題欄**不属于零件**，必须排除。

难点在于：

| 难点 | 说明 |
| --- | --- |
| 图元是断开的 | 一个零件由轮廓线、中心线、剖面线、尺寸线、引出线、文字等数十个互不相连的像素团组成，直接取连通域会碎成几十块 |
| 干扰物同构 | 表格 / 标题栏也是「密集线条 + 文字」，与零件在像素层面没有本质区别 |
| 版式不固定 | 不同图纸表格宽度不同，用固定比例遮蔽右侧，宽图上会把右侧零件一起抹掉 |
| 外框陷阱 | 图纸四周有包围全图的外框，它会把所有内容连成一整块，形成巨大的假零件 |
| 分辨率大 | A1 @300 DPI 约 9933 × 7016 px（约 7000 万像素），单通道图 70 MB / 三通道 209 MB |

因此**分割判定本身不做 OCR、不做矢量化、不做文字理解**，只做「图像形态学 + 几何统计」层面的版面切割，
用一套可解释、可调参的规则把「零件视图」当作「一块够大、够密、位置合理的像素团」来定位。

> 唯一例外：所有零件框定稿之后有一个**只读**的附加步骤（3.8 阶段 8），
> 把 PDF 文字层中落在每个零件框内的文字及其坐标一并落盘
> （`parts_info.json` 的 `texts` 字段 + `parts_text.txt`）；
> 同时把**零件框以外**的文字也留档：表格 / 标题栏区按「表 → 行 → 单元格」重组，
> 页边注记等归为「其它未归属」（3.9 → `outside_info.json` + `outside_text.txt`）。
> 它只读取、不参与任何框选 / 合并决策，因此开启或跳过都不影响分割结果。

## 2. 总体流水线

```

                ↓
[1] 光栅化      PDF → PDFium(Docnet) → BGRA → 白底合成 → BGR Mat      （PdfRenderer.cs）
                位图 → Cv2.ImRead                                     （PartSplitterService.cs）
                ↓  BGR 8UC3，尺寸 W×H（A1@300DPI ≈ 9933×7016）
[2] 预处理      BGR→灰度 → 自适应反向二值化（墨迹=255，背景=0）        （PartDetector.cs）
                ↓
[2.5] 图框擦除  擦掉四周贯穿页边的长横线 / 长竖线（防止图框把内部视图粘成一团）
                ↓  单通道 8UC1，前景=255                          → debug_01_binary.png
[2.6] 表格块    （仅 PDF，只读）PdfPig 取词 → 行/列结构 → 判定表格 / 表題欄矩形
                ↓  得到若干「只含文字的矩形」                      （PartTextExtractor.cs）
[3] 表格遮蔽    优先按表格块精确涂黑；无文字层 / 未检出时退回整列遮蔽
                ↓                                                → debug_02_masked.png
[4] 形态学聚合  闭运算(2 次) + 膨胀(1 次)，矩形核 kw×kh
                ↓  同一零件的碎散图元连成一个"团"                 → debug_03_dilated.png
[5] 轮廓筛选    FindContours → 面积 / 宽高 / 占屏比 / 遮蔽线 四道过滤
                ↓  （块遮蔽时另丢弃「整块落在表格列带内」的表格残片）
[6] 边距扩展    每框四周 +Padding，clamp 到画布内
                ↓
[7] 重叠合并    交集占小框比例 > 30% → 取并集，迭代至稳定

[8] 排序裁切    按 Y 升序编号 → 从原图（彩色）裁切 → Part_01.png …
                ↓
[9] 文字坐标    （仅 PDF，只读）PdfPig 取词框 → pt→px 换算 → 按重叠率归属各零件图
                ↓                                                → parts_text.txt
[10] 框外文字    （仅 PDF，只读）框外的词按遮蔽线分成「表格区 / 其它」

                                + 01_アッセンブリ図_要領図.csv（仅アッセンブリ図）
```

命令行、界面、对外接口共用同一份实现：`CommandLineRunner` / `MainForm` / `SplitApi` 都只是构造 `DetectorOptions`，
然后调用 `PartSplitterService.Run()`，因此三条入口的行为、参数、日志完全一致。
批量处理（界面选文件夹 / 粘文件夹路径 / 命令行传文件夹）多一层 `BatchRunner`：它只负责「列 PDF → 逐张调用
`PartSplitterService.Run()` → 汇总」，分割算法本身一行不改。

**输入路径怎么给**：界面上的「输入路径」框可直接编辑，点「浏览…」/「选择文件夹…」、拖拽、或直接把路径粘进去
（`Ctrl+V`）都行。粘贴时会先过 `MainForm.NormalizePath`：去掉最外层引号（资源管理器「复制为路径」给的是
`"D:\図面"`）、多行只取第一行、`file:///D:/図面` 转成本地路径 —— 否则带引号的字符串 `Directory.Exists`
判定为不存在，按钮会一直是灰的。粘完按 `Enter` 等同于点开始。

**输出位置**（与下游 AI 环节的约定）：结果默认写到所选图纸所在目录下的
`AiAppData\<图纸名>\`，即选 `D:\图纸\H310A20009.pdf` → 结果在 `D:\图纸\AiAppData\H310A20009\`
（界面选好文件后自动填这个路径，命令行省略输出目录时同样如此）；同目录的多张图纸各占一个子文件夹，
互不覆盖。多页 PDF 的第 2 页起子文件夹为 `H310A20009_P2`、`_P3`…，避免逐页分割时互相覆盖。
显式给出输出目录时按给定的路径，不再加 `AiAppData`；目录不存在时由 `PartSplitterService.Run()` 创建。

**批量模式的输出根目录**：输入是文件夹时，界面 / 命令行给出的那个路径是「根」，
每张图纸再各自落到 `<根>\<图纸名>\`；根留空时取 `<输入文件夹>\AiAppData\`
（`DetectorOptions.GetDefaultBatchOutputDirectory`）。这样批量结果与单张结果
**树形结构完全同构**，下游 AI 环节按 `<根>\<图纸名>\` 取文件即可，不需要区分是单张跑的还是批量跑的。
批量逐张串行执行（PDFium / OpenCV 都是进程级重资源，并行只会互相抢内存），
单张失败（文件损坏、页码超出该 PDF 页数等）只记 `[ERROR]` 并继续后面的图纸，
最后打印 `[批量完成] 共 N 张：成功 a / 失败 b / 零件合计 c`。

## 3. 阶段详解

### 3.1 阶段 1：光栅化（PDF → 像素矩阵）

代码：`PdfRenderer.RenderPage()` / `PdfRenderer.GetPageCount()`

**为什么必须栅格化**：PDF 里的线条可能是矢量化路径、嵌入式图像、甚至被裁剪过的变换矩阵，
逐个解析图元需要完整的 PDF 内容流解释器，且不同 CAD 导出的结构千差万别。
栅格化成像素矩阵后，所有图纸都变成同一类问题，用同一套 OpenCV 操作即可处理，稳健性最高。

**DPI 换算**：PDF 内部单位是 pt（1 pt = 1/72 inch），PDFium 用缩放因子渲染：

```
scalingFactor = dpi / 72.0                     // 300 DPI → 4.1667
PageDimensions(scalingFactor)  →  页面像素 = 页面 pt 尺寸 × scalingFactor
A1 (841 × 594 mm = 2384 × 1684 pt) × 4.1667 ≈ 9933 × 7016 px
```

**关键陷阱：透明背景**

PDFium 的 `GetImage()` 返回 **BGRA** 字节数组，PDF 背景是透明的（A=0，RGB=0）。
若直接 `BGRA→BGR`，透明背景与黑色线条都会变成 `(0,0,0)`：**整张图全黑**，
自适应二值化后几乎全为前景，后续全部失效。

因此 `CompositeOverWhite()` 先把 BGRA 原地合成到白底再转换：

| 原 alpha | 处理 |
| --- | --- |
| `255`（不透明） | 保持原色 |
| `0`（全透明） | 置为白色 `(255,255,255)` |
| `0 < a < 255`（半透明） | 线性混合：`c·α + 255·(1−α)` |

**内存代价**：A1@300 DPI 时，`byte[4W·H]` ≈ 279 MB、`CV_8UC4` Mat ≈ 279 MB、`CV_8UC3` Mat ≈ 209 MB，
仅渲染阶段峰值就接近 0.8 GB，加上后续 4 张单通道图（各 70 MB），建议 **x64 + 2 GB 以上可用内存**；
内存紧张时用 `--dpi 150`（像素量、内存均降为 1/4，代价是细线变模糊）。

位图输入（扫描件）直接 `Cv2.ImRead(path, ImreadModes.Color)`，不经过 PDFium。

### 3.2 阶段 2：灰度化 + 自适应反向二值化

代码：`PartDetector.ToGray()` / `PartDetector.AdaptiveBinarize()`

```csharp
Cv2.CvtColor(src, gray, ColorConversionCodes.BGR2GRAY);   // 去色差，后续只看明暗

Cv2.AdaptiveThreshold(gray, binary,
    maxValue:       255,
    adaptiveMethod: AdaptiveThresholdTypes.GaussianC,     // 邻域加权均值（高斯窗口）
    thresholdType:  ThresholdTypes.BinaryInv,             // 反向：暗→255
    blockSize:      max(3, 奇数化(AdaptiveBlockSize)),    // 默认 51
    c:              AdaptiveC);                           // 默认 10
```

**为什么用自适应而不是全局阈值（Otsu）**：扫描件的背景明暗不均（边缘发灰、有阴影），
全局阈值会把灰底判成前景；自适应阈值只与局部 `blockSize` 邻域比较，
`binary(x,y) = 局部高斯均值 − C > gray(x,y) ? 255 : 0`，能适应逐块的光照差异。
纯矢量 PDF 导出时背景是纯白，自适应同样适用，因此两者共用一套参数。

**为什么用 `BinaryInv`（反向）**：让语义变成「**墨迹 = 255 = 前景**」。这一约定决定了后面三步：

| 后续操作 | 依赖的前景约定 |
| --- | --- |
| 列墨迹统计 `Cv2.CountNonZero(列)` | 直接数到的就是"这一列有多少墨迹像素" |
| 形态学 `Dilate` / `Close` | 膨胀的是真实的线条，空白处才能被"填" |
| `FindContours` | 得到的是图元外轮廓，而不是"背景洞"的轮廓 |

若使用正向阈值，"墨迹"会变成 0，上述三步全部要额外取反，容易出错。

**参数约束**：OpenCV 要求 `blockSize` 为 ≥3 的奇数，代码中已自动纠正为奇数。
`c` 越大越严格（去噪多、淡线易丢）；扫描件建议 `blockSize 51~101`、`c 5~15`。

### 3.3 阶段 3：图框擦除 + 表格区遮蔽

代码：`PartDetector.RemovePageFrameIfEnabled()` / `PartTextExtractor.DetectTableAreas()` /
`PartDetector.MaskTableAreas()` / `DetermineMaskStartX()` / `DetectTableColumnStart()` / `MaskRight()`

**目的**：部品表、タイプ表、詳細表、表題欄是「表格线 + 文字」组成的密集区域，
形态学膨胀后会成为一个或多个面积巨大的团，必然被误判为零件。
与其事后过滤，不如在进入形态学之前直接把这块区域**刷成纯黑（背景）**，
让它从物理上不存在——这样后续所有步骤都不需要知道"有表格"这件事。

本阶段先擦图框（3.3.1），再遮蔽表格（3.3.2 ~ 3.3.4）。

#### 3.3.1 图框擦除（`RemovePageFrame`，默认开启）

图框是贴近页边、几乎贯穿整幅的矩形线（构成「図枠」+ 表題欄边框）。留着它有两个害处：

| 害处 | 现象 |
| --- | --- |
| ① 与内部视图粘连 | 视图的尺寸线/引出线接到图框上，膨胀后「图框 + 内部全部视图」连成一团，整框被当成一个零件（框内所有内容一起输出） |
| ② 被遮蔽线截断后面积变小 | 遮蔽吃掉图框右半段后，剩下「C 形残片」面积占比降到 `MaxBboxFillRatio` 以下，**反而躲过外框过滤**——输出一张「半页图」，这正是 H310A20009 的故障现象 |

判据（逐行 / 逐列统计墨迹）：

```
一行被判为图框横线 ⇔ CountNonZero(binary[y]) ≥ W × PageFrameSpanRatio(0.70)
                    且 y 位于顶部 / 底部 PageFrameEdgeRatio(0.10) 带内
一列被判为图框竖线 ⇔ CountNonZero(binary[x]) ≥ H × PageFrameSpanRatio(0.70)
                    且 x 位于左侧 / 右侧 PageFrameEdgeRatio(0.10) 带内
命中后把该行（列）连同上下（左右）各 2 px 一起涂黑
```

"只擦页边 10%、只擦贯穿 70%"这两条约束保证不会误擦零件本身的长中心线：

| 图纸 | 命中 | 说明 |
| --- | --- | --- |
| `H310A20009.pdf`（A4 横） | 横线 2 条 / 竖线 2 条 | x=26/27、3477/3478；y=9/10、2452/2453 |
| `H310U10004.pdf`（A1 横） | 横线 5 条 / 竖线 4 条 | 图框 + 分格线 |

> 擦掉图框后，`MaxBboxFillRatio`（占屏比过滤）就不再承担"拦图框"的职责，
> 因此在块遮蔽模式下它的实际上限被放宽到 `max(MaxBboxFillRatio, 0.60)`——
> 否则「竖排 4 个断面部」这种经引线相连、面积占比 25% 的正常大块会被误杀。

**导出时要再擦一次**：本步擦的是检测用的二值图，而裁切 PNG 取自**原始彩色图**。
若不在裁切前把同样的行 / 列（`_frameRows` / `_frameCols`，±2px 一致）涂白
（`PartDetector.ErasePageFrameOn()`），输出图就会带着图纸的左 / 上 / 下边框、却缺右边框
（右边框落在零件框之外），看上去像「整页图纸被竖着切了一刀、右边没了」。

#### 3.3.2 表格块精确遮蔽（`MaskTableBlocks`，默认）

**为什么要换掉整列遮蔽**：列墨迹延伸法（3.3.4）的前提是「表格区与零件区在 X 方向可分」。
当图纸把部品表放在**右上角**、零件视图放在**中部下方**时，两者的 X 投影重叠，
从最右列往左延伸的"密实带"会一路吃进零件区：

```
H310A20009.pdf（3508×2479）实测列墨迹：
  x 1618 处 ink=19 < 阈值 25   ← 密实带在这里断开
  x 1622 ~ 3477 每列 ink ≥ 25  ← 但这 54% 宽度里既有部品表，也有中部大断面図
  → 遮蔽线落在 1622，中部大断面図（x≈1400~3300）右侧 2/3 被涂黑，「一张图被切掉一半」
```

**做法**：用 PDF 文字层先把「表格 / 表題欄」矩形推断出来（判据见 3.3.5），
然后只涂黑这些矩形（四周外扩 `TableMaskPadding`=30 px 吃掉表格线框），其余像素原样保留：

```csharp
foreach (area in tableAreas)                       // 文字层给出的表格矩形
    result[IntersectPage(area ± TableMaskPadding)] = 0;
```

同一张 H310A20009 的实测对比：

| 遮蔽方式 | 遮蔽范围 | 检出零件 | 结果 |
| --- | --- | --- | --- |
| 整列遮蔽 | X ≥ 1622 全高 54% | 1 | 只剩左侧一列，且被图框残片连成 683×2461（半页图） |
| 块遮蔽 | 4 个文字矩形（部品表 / 切断表 / NC 表 / 表題欄） | 2 | 左侧 4 个断面 1334×2479（完整）+ 中部大断面 1783×866（完整） |

**副作用与兜底**：块遮蔽只擦掉"检出的表格"，表格之间的连接线 / 空白行仍可能连成**表格残片**伪零件。
因此块遮蔽模式下额外用列墨迹法算出「表格列带」左边界 `_tableBandStartX`，
凡是**整块都落在列带内**的候选一律丢弃（H310U10004 实测因此丢掉 10 个残片，零件数 16 → 13）。

#### 3.3.3 旧做法：固定比例（`--fixed-mask`，等价于 `AutoMaskRightColumn=false`）

```
X_mask = round(W × (1 − RightMaskRatio))        // 默认 0.50 → 遮掉右半页
rect(X_mask, 0, W − X_mask, H) = 0
```

实现简单、可预期，但它**假设「表格永远在右侧 50% 以内」**。一旦图纸是宽幅版式、
右侧还画了零件视图，就会误伤——详见第 6 节的实测案例（右侧「戸当り」整块被抹掉）。

#### 3.3.4 兜底做法：列墨迹延伸法

核心观察（表格区与零件区的判别依据）：

```
        表格区                          零件区
┌──┬──┬──┬──┬──┐              ┌───┐        ┌───┐
│  │  │  │  │  │              │   │        │   │
├──┼──┼──┼──┼──┤              │   │        │   │
│  │  │  │  │  │              └───┘        └───┘
└──┴──┴──┴──┴──┘                ↑            ↑
  每一列都被横线/文字穿过         零件之间必然有"几乎空白"的列
  → 列墨迹稳定 ≥ 图高的 1%      （引线/尺寸线不会整列贯穿，也不会跨越两个零件）
```

* 表格的**任意一列**，从顶到底都会撞到表格横线（或字符笔画）→ `ink[x]` 稳定偏高；
* 零件区的列是稀疏的，且**零件与零件之间必然存在细窄空白列**——这正是"两个零件是分开的"这一事实的直接体现。

算法（`DetectTableColumnStart`）：

```
ink[x]  = CountNonZero(binary 第 x 列)              // 逐列统计前景像素数
lastInk = 最右侧 ink[x] > 0 的列                     // 忽略右侧空白页边
if (lastInk <= 0)              → 检测失败
T       = max(8, round(H × AutoMaskColumnInkRatio))  // 默认 0.010·H，A1@300DPI ≈ 70 px
x       = lastInk
while (x > 0 && ink[x] >= T)   x--                  // 从右往左走"密实段"
start   = x + 1                                     // 密实段最左一列 = 表格区左边界
if (start >= lastInk)          → 检测失败            // 整页密实，无分界列
return start
```

`DetermineMaskStartX` 带兜底的选择逻辑：

```
fallbackX = clamp(round(W × (1 − RightMaskRatio)), 0, W)

if (!AutoMaskRightColumn)                        → 用 fallbackX     （旧行为）
autoX = DetectTableColumnStart(binary)
if (autoX < 0)                                   → 用 fallbackX     （找不到密实段）
maskedRatio = (W − autoX) / W
if (maskedRatio < AutoMaskMinMaskedRatio(0.05)
 || maskedRatio > AutoMaskMaxMaskedRatio(0.60))  → 用 fallbackX     （结果离谱，视为误判）
                                                 → 用 autoX         （正常）
```

两种边界保护的含义：

| 保护 | 触发的典型情形 |
| --- | --- |
| 遮蔽宽度 < 5% | 图纸右侧没有成片表格，只扫到一根边框 → 不遮蔽，交给比例兜底 |
| 遮蔽宽度 > 60% | 找不到分界列（整页被图元占满 / 大幅图片）→ 视为误判，退回比例 |

**日志可追溯**：实际采用哪条分支都会输出一行，便于现场排查：

```
[INFO] 右侧遮蔽：自动检出表格/标题栏区 X=7074（遮蔽右侧 29%，较固定比例 50% 保留更多图纸内容）
[INFO] 右侧遮蔽：自动检测 X=1234（宽度 88%），超出容忍区间 5%~60%，改用固定比例 50% → X=4966
[INFO] 右侧遮蔽：未检出表格/标题栏区，改用固定比例 50% → X=4966
[INFO] 右侧遮蔽：固定比例 50% → X=4966（自动检测已关闭）
```

**遮蔽动作本身**（`MaskRight`）：在二值图副本上把 `[X_mask, W) × [0, H)` 全部置 0，
同时把 `X_mask` 记入字段 `_maskStartX`，供阶段 5 复用（保证「遮蔽范围」与「筛选范围」一致）。

**阈值敏感性**（同一张 A1 图纸实测）：`AutoMaskColumnInkRatio` 取 0.005~0.011（40~80 px）时
检出边界稳定在 `X = 7074 ~ 7151`。说明该判据对阈值不敏感——它在找"结构性分界列"，
而不是某个精确像素值。

#### 3.3.5 表格块判据（区分「表格」与「散落标注」）

代码：`PartTextExtractor.DetectTableAreas()`（只读文字层，不需要遮蔽线，也不需要零件结果）

```
① 取词 → 转页面像素（与 3.8 同一套换算）
② 分行：纵向中心差 ≤ 0.6 倍字高；行内按间隙 > max(24px, 1 倍字高) 拆单元格
③ 拆段：行内相邻单元格间隙 > max(120px, 8 倍字高) 断开
        ── 同一 Y 上「左侧零件标注」与「右侧部品表」会被并成一行，必须先拆开，
           否则会得到一张「跨页宽表」，遮蔽时把左侧零件图一起涂黑
④ 分块：与已有块的末行纵向紧邻（间隙 ≤ max(60px, 1.5 倍行高)）
        + 单元格数相差 ≤ 3 + 横向范围重叠 ≥ 50%
⑤ 判定（满足任一形态 + 结构证据 + 尺寸下限）：
     形态 A 多行多列：行 ≥ 3，每行单元格数中位数 ≥ 3，且 ≥ 2 行有 3 格以上
     形态 B 短表：    行 = 2 且列数 ≥ 4（如 2 行 7 列的型番表）
     形态 C 密集文本：行 ≥ 3，行距规律性 ≥ 0.80，字符数 ≥ 24，每行宽度中位数 ≥ 块宽 50%
                      ── 表題欄这类大量合并单元格的表（每行只有 1~2 格、列对不齐）
     结构证据：列对齐率 ≥ 0.60（形态 A/B）或行距规律性 ≥ 0.80（形态 C）
     尺寸下限：列数 ≥ 3，块宽 ≥ 图宽 4%，块高 ≥ 图高 1.2%，块面积 ≤ 全图 45%
```

两条"结构证据"是区分表格与标注的关键：

| 证据 | 定义 | 真表格 | 散落的尺寸标注 |
| --- | --- | --- | --- |
| 列对齐率 `RowAlignment` | 相邻行中，本行单元格中心能在上一行找到对应列（容差 max(20px, 0.8 倍字高)）的比例 | 0.9 ~ 1.0 | 0 ~ 0.3 |
| 行距规律性 `RowPitchRegularity` | 相邻行中心距落在「中位数 0.5~1.6 倍」的比例 | 0.86 ~ 1.0 | 0 ~ 0.5 |

`H310A20009.pdf` 实测（✓ 为最终遮蔽的 4 块）：

| 块 | 行 | 列 | 列对齐 | 行距 | 判定 |
| --- | --- | --- | --- | --- | --- |
| 部品表 + 切断表 | 22 | 20 | 0.88 | 0.86 | ✓ |
| NC95/NC115 型番表 | 3 | 8 | 0.94 | 1.00 | ✓ |
| 注記 + 表題欄上部 | 3 | 3 | 0.00 | 1.00 | ✓（形态 C） |
| 表題欄右下格 | 4 | 3 | 0.33 | 1.00 | ✓（形态 C） |
| 中部大断面図的尺寸标注 | 3 | 3 | 0.00 | 0.33 | ×（形态/证据都不满足） |

#### 3.3.6 三种遮蔽方式的选择顺序

```
① MaskTableBlocks && 文字层检出表格块（PDF）
       → 块遮蔽 + 丢弃「整块落在表格列带内」的残片
       → 若一个零件都没检出，记 WARN 并降级到 ②
② AutoMaskRightColumn（默认开）
       → 列墨迹延伸法（3.3.4），带 5%~60% 宽度保护，失败退回 ③
③ 固定比例 RightMaskRatio（默认 0.50）
```

`TableStartX`（= `PartDetector.MaskStartX`）在三种方式下都会被写入，供 3.9 把框外文字
分成「表格区 / 其它」：块遮蔽时取「中心落在右半页的表格块」的最小左边界
（左下角表題欄不参与，避免把整页文字都算成表格区）。

### 3.4 阶段 4：形态学聚合（把碎图元糊成一个零件）

代码：`PartDetector.DilateForGrouping()`

```csharp
kernel = GetStructuringElement(MorphShapes.Rect, new Size(kw, kh));  // 默认 60 × 10
MorphologyEx(binary, tmp, MorphTypes.Close, kernel, iterations: 2);  // 先闭：填小洞、连虚线
Dilate(tmp, out, kernel, iterations: 1);                             // 再膨：让相邻块接触
```

**闭运算（先膨胀后腐蚀）**：把同一零件内部"间距小于核尺寸"的断裂处连起来，
同时不显著放大零件外部边界——虚线、断笔、细缝因此被补齐。

**膨胀（再向外扩）**：保证同一零件的各个子块（零件本体 + 它的尺寸标注）在连通域意义上真正接触，
形成一个整体"团"。

**为什么用各向异性矩形核（宽 60 × 高 10）**：
零件视图的尺寸链、引出线、编号主要沿**水平方向**铺开；
而相邻零件之间的上下间距相对紧凑。因此横向聚合半径必须远大于纵向：
`kw` 负责把左右散开的标注拉进同一个团，`kh` 只做轻微纵向桥接，避免把上下相邻的两个零件粘成一个。

| 现象 | 调整方向 |
| --- | --- |
| 一个零件被切成 2~3 个框（数量偏多、单框偏小） | 增大 `kw` / `kh` 或 `DilateIterations` |
| 相邻两个零件粘成一个框（数量偏少、单框偏大） | 优先减小 `kh`，其次 `kw`、`DilateIterations` |
| 整页糊成一块（框≈全图，随后被占屏比过滤掉） | 核过大，必须减小 |

### 3.5 阶段 5：轮廓提取与几何筛选

代码：`PartDetector.ExtractPartRects()`

```csharp
Cv2.FindContours(dilated, out contours, out hierarchy,
                 RetrievalModes.Tree, ContourApproximationModes.ApproxSimple);
```

`RETR_TREE` 会建立完整的包含层级（外轮廓 / 内孔 / 孔中再嵌套），
当前把返回的扁平轮廓列表当作候选，层级信息保留给后续扩展
（例如做"孔中孔"这类零件内部结构分析时需要它）。

**四道过滤器**（顺序执行，任一不过即丢弃）：

| # | 判据 | 默认值 | 拦掉什么 |
| --- | --- | --- | --- |
| ① | `ContourArea(contour) ≥ MinContourArea` | 25000 px² | 孤立的尺寸数字、引线、噪点 |
| ② | `bbox.Width ≥ 200`、`bbox.Height ≥ 80` | MinBoundingWidth/Height | 单根细长刻线、单独一条边框线 |
| ③ | `bbox面积 / 全图面积 ≤ MaxBboxFillRatio` | 0.25 | **图纸外框**（包裹全图，占比常 40%~50%），以及糊成整页的团 |
| ④ | `bbox.Left < rightBoundary` | `X_mask` | 完全落在表格区内、自动遮蔽万一漏掉的团（第二道保险） |

第 ④ 条特别说明：判据用的是**外接框左边界**而不是中心点。
宽零件可能横跨遮蔽线——用左边界可以保住"大部分在图纸区"的零件，
只有整体都在表格区里的才丢。早期版本用中心点判断，导致遮蔽线放宽后，
个别零件仍因"中心点落在比例线右侧"被丢弃；现在「遮蔽」与「筛选」共用同一个 `_maskStartX`。

同时这里会输出一次截断告警（只报第一例）：

```
[WARN] 有零件贴近遮蔽边界 X=7074，右侧可能被切
       可减小「右侧遮蔽」比例或调整遮蔽阈值
```

### 3.6 阶段 6：边距扩展与重叠合并

**边距扩展**（`AddPadding`，默认 30 px）：每个外接框四周扩大 `Padding`，
避免尺寸标注箭头、文字被切在框外；扩展后 clamp 到 `[0,W] × [0,H]`，不会越界
（越界的 ROI 会让 OpenCV 直接抛异常）。

**重叠合并**（`MergeOverlappingRects`，阈值 `MergeOverlapThreshold = 0.30`）：

```
重叠率 = 交集面积 / min(面积i, 面积j)
若 重叠率 > 0.30 → 两框取并集、删除其中一个，重新扫描，直到一轮下来无任何合并
```

* 分母用 `min` 而不是并集面积：当一个框完全包含另一个框时 `交集/较小框 = 1.0`，
  包含关系也能稳定触发合并（"零件本体框"与"其子块框"正是这种情形）；
* 迭代到稳定（`while (anyMerge)`）：合并出的大框可能又与第三个框重叠，需要多轮收敛；
* 合并前先按 `Y`、`X` 排序，保证结果确定、可复现。

#### 3.6.1 表格残片筛除（`DropTextHeavyParts`，默认开启）

代码：`PartDetector.DropTextHeavyRects()` + `PartTextExtractor.ReadTextLineBoxes()`

表格的框线若没被完全遮蔽（块遮蔽的矩形是按**文字外接框**外扩 `TableMaskPadding` 得到的，
不一定覆盖整条表格线），残留的线框会形成一个细长连通域，通过 3.5 的四道过滤，被当成零件
输出——图里没有零件视图，只有表題欄 / 変更履歴表的几行字。

判据只看文字：

```
文字行占比 = Σ(每条文字行的外接框 ∩ 该块框架) ÷ 该块框架面积
占比 ≥ TextHeavyRatio（默认 0.60） → 判定「不是要分割的零件图」，丢弃
```

* **文字行**的划分与 3.8 的 `GroupIntoLines` 完全相同（同一套 Y 容差分组），所以行框就是
  `parts_text.txt` 里那一行字实际占的矩形 —— 不是词级紧贴字形的小框；
* 计面积用**交集**：跨在块边界上的行只把落在块内的那部分算给该块；
* 词 / 行框互相重叠时面积和对块面积封顶（`textArea > area → area`），占比不会超过 1；
* 筛除发生在 **3.7 导出 PNG 之前**，因此 `Part_NN.png` 的编号仍然连续，不会留下空号，
  `parts_info.json` 的 `index` 也是连续的。

为什么这条判据分得开：表格的每一行都横跨单元格、行与行首尾相接，行框几乎铺满整块；
零件视图上的文字只有零散的尺寸数字和引线注记，一行只有几个字。实测（300 DPI）：

| 图纸 | 真正的零件视图 | 表題欄 / 変更履歴表 残片 |
| --- | --- | --- |
| `H310U10004.pdf` | 11 块：0.029 ~ 0.459（最高一块是标注最密的「鴨居」详图） | 2 块：0.652、0.720 → 丢弃 |
| `H310A20009.pdf` | 2 块：0.063、0.106 | 无 |

日志（`H310U10004.pdf` 实测）：

```
[DROP] 文字行占比过高，判定不是零件图：x=674 y=6212 w=1419 h=156 文字行占比 0.65
[DROP] 文字行占比过高，判定不是零件图：x=824 y=6333 w=2374 h=158 文字行占比 0.72
[INFO] 文字行占比筛除：丢弃 2 个 / 保留 11 个（阈值 0.60）
```

配套行为：

* 位图输入没有文字层 → `ReadTextLineBoxes` 返回空列表，筛除自动跳过（不做 OCR）；
* **全部**候选都被判为文字块时保留原样并告警（`[WARN] … 已全部保留（避免输出为空…`），
  避免「整页都是文字说明」的图纸输出空结果；
* `--debug` 时逐块打印 `[RATIO] … 文字行占比 0.xxx`，用于决定阈值取多少；
* `--keep-text-heavy` 整体关闭本筛除；`--text-ratio <N>` 改阈值（调低更激进，调高更保守）。

### 3.7 阶段 7：排序、裁切与坐标换算

代码：`PartDetector.ExportParts()` + `PartSplitterService.SavePartsJson()`

1. 按 `bbox.Y` 升序排序（即"从上到下"的阅读顺序），编号 `Part_01.png`、`Part_02.png` …；
2. **从原图裁切**（彩色 / 灰阶 BGR），不是从二值图裁——二值图只用于定位，输出必须保留原始线条外观；
3. 裁切用 `new Mat(original, roi)`（ROI 视图，零拷贝）→ `SaveImage()`；
4. 坐标换算：

   ```
   mmPerPx = 25.4 / RenderDpi          // 300 DPI → 0.084667 mm/px
   PdfX_mm = PixelX × mmPerPx          // Y / W / H 同理
   ```

   注意：这里给出的是**图像坐标系（左上原点、Y 向下）**的毫米值，
   与 PDF 原生坐标系（左下原点、Y 向上）方向相反；调用方若需要 PDF 原生坐标，
   需自行换算 `Y' = 页面高mm − Y − H`；

5. 结果写入 `parts_info.json`（UTF-8 无 BOM）：

   ```json
   [
     {
       "index": 1,
       "fileName": "Part_01.png",
       "pixel": { "x": 2663, "y": 539, "w": 2160, "h": 1055 },
       "pdf_mm": { "x": 225.47, "y": 45.64, "w": 182.88, "h": 89.32 },
       "texts": [
         {
           "text": "鴨居",
           "pixel":  { "x": 3619, "y": 1045, "w": 190, "h": 77 },
           "local":  { "x": 956,  "y": 506,  "w": 190, "h": 77 },
           "pdf_mm": { "x": 306.41, "y": 88.48, "w": 16.09, "h": 6.52 }
         }
       ]
     }
   ]
   ```

   该文件是「零件图 → 原图纸坐标」的桥梁：后续识别模块可据此把零件图映射回图纸位置，
   也能判断两张零件图是否来自同一图纸的相邻区域。
   `texts` 字段由 3.8 阶段填充；位图输入时为空数组，其余字段与旧版本完全一致（向后兼容）。

### 3.8 阶段 8：文字坐标提取（输出阶段，只读，不参与分割）

代码：`PartTextExtractor.Attach()` / `PartTextExtractor.BuildLines()`（`--merge-text-lines`）/
`PartTextExtractor.BuildWordLines()`（默认）/ `GroupIntoLines()` + `PartSplitterService.SaveTextReport()`

本阶段在**零件框全部定稿之后**运行，只读不写：日志、坐标、裁切结果都与不做本阶段时完全一致。

**为什么要做**：分割结果原本只有坐标，下游要知道"这张图是什么部番 / 什么材质 / 有没有特殊注记"，
就必须知道图上写了什么、写在哪里。CAD 导出的 PDF 一般保留完整文字层（非扫描件），
可直接读出文字与词框，比 OCR 精确且零误差（OCR 对日文假名 + 尺寸数字混排误识率很高）。

**坐标换算**（与 3.1 的 `dpi/72` 是同一套比例，但 Y 方向相反）：

```
PdfPig 词框：PDF 用户坐标（pt，左下原点，Y 向上；注意 Top > Bottom）
处理图像    ：渲染像素（左上原点，Y 向下）

scaleX = 图像宽px / 页面宽pt          scaleY = 图像高px / 页面高pt
x_px   = Left × scaleX
y_px   = (页面高pt − Top) × scaleY            ← Y 轴翻转，用 Top 而不是 Bottom
w_px   = (Right − Left) × scaleX
h_px   = (Top − Bottom) × scaleY
```

* 两个方向**分别**算缩放比（不复用 `dpi/72`）：渲染取整会使图像尺寸与 `页面pt × dpi/72`
  差 1~2 px，分别归一后像素坐标才能与裁切框严格对齐；日志会打印实际比例
  `缩放 4.1665×4.1663` 供核对；
* 同一套 `mmPerPx = 25.4 / dpi` 换算毫米坐标，与 3.7 的 `pdf_mm` 完全一致。

**归属规则**（一个词落在哪张零件图上）：

```
重叠率 = (词框 ∩ 零件框) 面积 / 词框面积
重叠率 ≥ 0.50  →  该词属于这张零件图
```

* 用面积占比而不是中心点：跨在裁切边缘的尺寸文字，中心点可能刚好落在框外，
  但它确实属于这张图；阈值 0.50 保证一个词绝不会被两张图同时收录（零件框之间本身不重叠，见 3.6）；
* 落在表格 / 标题栏区（3.3 遮蔽线右侧）的词不属于任何零件框，不会进 `texts`——
  实测 `H310U10004.pdf` 全页 630 个词，只有 50 个落进 12 个零件框；其余 580 个词由 3.9 单独留档。

**每个词记录三套坐标**：

| 字段 | 含义 | 用途 |
| --- | --- | --- |
| `pixel` | 页面绝对像素（左上原点） | 叠回整页定位、与原图对照 |
| `local` | 相对所属零件图左上角 | 直接在 `Part_NN.png` 上画框 / 取子图 |
| `pdf_mm` | 页面毫米（`px × 25.4 / dpi`） | 与图纸标注尺寸对照 |

**文字清单粒度**（只影响人眼可读的 `parts_text.txt`；`parts_info.json` 里始终是词级原始坐标）：

默认**一个词一行**（`SplitTextToWords = true`），每条记录的坐标就是该词自己的外接框，
于是同一水平线上的「编号 + 名称 + 视图名」会拆成三条：

```
y=1070  x=3051  w=42    h=58   局部(388,531)  ①1
y=1045  x=3619  w=190   h=77   局部(956,506)  鴨居
y=1026  x=4197  w=160   h=77   局部(1534,487)  G部
```

行序仍是自上而下、行内从左到右 —— 分行规则与下面的「按行合并」完全相同
（共用 `GroupIntoLines()`），所以相邻的这几条就是原图上同一行的词，只是各自带着自己的框。
理由：合并成 `①1 鴨居 G部` 只有一个并集坐标，下游按行解析时分不清
`鴨居` 和 `G部` 各自的框落在哪里。

需要还原成「一句话 + 并集坐标」时加 `--merge-text-lines`（`SplitTextToWords = false`）：

```
判行：|两词纵向中心差| ≤ 0.6 × 字高
排序：行内按 X 升序
拼接：相邻词水平间隙 > 0.5 × 字高 → 补一个空格，否则直接相连（适应中/日文紧排）
```

```
y=1026  x=3051  w=1306  h=102   局部(388,487)  ①1 鴨居 G部
```

而上下相邻的尺寸链、注记行不会被粘成一行（各自纵向中心差超过 0.6 倍字高）。

若某个词是圈号标注的圈内数字，两种粒度下都在**它原来的位置**输出带圈形式
（`1` → `①1`，见 3.10 的 ⑦ 步）；词级原始文本和 JSON 都不变。

**位图输入**：PNG / JPG / TIF 没有文字层，本阶段直接跳过，日志提示
`位图输入没有文字层，跳过文字坐标提取`，`texts` 为空数组，`parts_text.txt` 中标注
`（该图范围未检测到文字）`。需要文字时请另行接入 OCR 引擎。

**实测输出**（`H310U10004.pdf`，300 DPI，11 张零件图）：

```

[TEXT] Part_05.png  1 个词     → 戸当り   页面(6034,1390) 局部(120,32)   ← 镜像对称，坐标几乎一致
```

### 3.9 阶段 9：框外文字与表格记录（输出阶段，只读）

代码：`PartTextExtractor.Attach()`（返回 `PageTextResult`）+ `BuildTables()` / `BuildColumns()` /
`BuildBlockList()` + `PartSplitterService.SaveOutsideJson()` / `SaveOutsideTextReport()`

**为什么要做**：分割结果只交付「零件视图」，而一张图纸的其余信息（部品表、タイプ表、表題欄、
底部注记、签署栏）同样是下游要读的内容。它们恰好就是零件检测时被遮蔽掉的区域——
既然 3.8 已经把文字层读进内存，顺手按版面结构落盘成本几乎为零（共用同一次 PDF 打开，
不再二次解析）。

**分组规则**（即「被分割部分以外」的划分）：

```
不落在任何零件框内（3.8 的 50% 重叠率口径）
  ├─ 词中心 X ≥ 遮蔽线 X_mask（PartDetector.MaskStartX）→ 表格 / 标题栏区
  └─ 其余                                              → 其它未归属（页边注记、签署栏等）
```

用词**中心 X** 而不是左边缘：跨在遮蔽线上的表格首列，其左边缘可能落在 `X_mask` 左侧，
用中心才不会漏。

**「表 → 行 → 单元格」重建**（`BuildTables`）：

```
① 分行    |两词纵向中心差| ≤ 0.6 × 字高                        （与 3.8 文字清单同一容差）
② 单元格  行内按 X 排序；与前一词的水平间隙 > max(24px, 1.0 × 字高) → 新单元格
          否则并入当前单元格（补空格规则同 3.8：间隙 > 0.5 字高才补空格）
③ 列号    本表内所有单元格按「中心 X」聚类，容差 max(16px, 0.6 × 平均字高)
          聚类序号 = 列号（推断值）
④ 分表    相邻行垂直间隙 > max(80px, 3 × 平均行高)
          或相邻行单元格数突变 > CellCountJumpTol(=2)  → 另起一张表
⑤ 外接框  表块 = 其所有单元格的并集；左边沿对齐到 X_mask，便于与零件区一眼分开
```

* 列号为什么用**中心**而不是左边缘：表格文字多为居中对齐，同一列里
  「番号」与「鬼目ナット（ブレーキ取付用）」这类长短悬殊的文字左边缘可差 200px 以上，
  中心却几乎重合——实测该表 91 个单元格因此只聚出 7 列（用左边缘会虚胖成 42 列）；
* 为什么还要「单元格数突变」这一条：图纸里上下紧邻、但列数完全不同的表之间往往**没有空白分隔**
  （实测 `H310U10004.pdf`：第 1~13 行 7 列部品表、第 14~35 行 15 列型枠表、后面另一张 8 列表），
  只靠垂直间隙会把三张表粘成一张，列号被拉到 42。加上这条后切成 10 张表。

**输出两份文件**：

| 文件 | 内容 |
| --- | --- |
| `outside_info.json` | 机器可读：`tables[]`（`name` / `pixel` / `pdf_mm` / `row_count` / `cell_count` / `rows[].cells[]`）+ `other_words[]`（词级 `text` / `pixel` / `pdf_mm`） |
| `outside_text.txt` | 人眼可读：第一节表格按「表 → 行 → 单元格」列出文字与坐标；第二节其它未归属文字与 `parts_text.txt` 同粒度（默认逐词一行，加 `--merge-text-lines` 则按行合并）（UTF-8 带 BOM） |

**实测输出**（`H310U10004.pdf`，300 DPI）：

### 3.10 阶段 10：圈号标注识别（输出阶段，只读）

**问题**：图纸上的引出编号是「一个圆圈 + 圈里的数字」，例如 ①1、②2。
圆圈是**图形**（矢量路径），数字才是文字层里的一个词——所以任何"复制文字"的方式拿到的都只是一个
孤立的 `1`、`2`，圈会丢，而且这些孤立数字会和尺寸标注里的数字混在一起，无法区分。

**做法**：把「圆」和「圈内数字」重新配成一条记录，输出带圈的 ① ② … 与坐标。

```
① 取页面矢量路径：page.ExperimentalAccess.Paths（PdfPig）
     每条 PdfPath 由若干 PdfSubpath 组成，命令为 Move / Line / CubicBezierCurve / Close …
     坐标已应用 CTM（内容流里的 0.12 cm 之类），与文字层的页面坐标同一口径
   ↓
② 扁平化成折线：直线取端点，贝塞尔按 8 等分采样
     CAD 画圆有两种常见写法——「四段三次贝塞尔」与「大量短直线折线」，扁平化后统一处理
   ↓
③ 整圆判定（全满足才算圈）：
     · 点数 ≥ 6；包围盒宽高比 ≥ 0.90（近正方）
     · 各点到外接中心的半径比 rMax/rMin ≤ 1 + CalloutRadiusTolerance（默认 1.15）
     · 八个方位（每 45°）都有点 —— 排除圆弧、半圆、圆角；四段贝塞尔圆的端点只落在
       4 个方位上，所以必须先扁平化再判方位，否则会全部漏检
     · 半径 ∈ [CalloutMinRadiusMm, CalloutMaxRadiusMm]（默认 0.8 ~ 12mm）
   ↓
④ 同心去重：离心距离 < 较小半径的一半 → 同一个圈（粗线圆会画成内 / 外两条路径）
   ↓
⑤ 与文字层配对：圆内必须有 1~3 位纯数字词，且尺寸装得进圈（数字高 ≤ 1.3 倍半径）
   ↓
⑥ 归属零件图：圆心落在哪张零件图的框内 → 记 PartIndex / 文件名 / 局部坐标
   ↓
⑦ 回填文字（parts_text.txt 专用）：对每个圈，在该零件图的词里找「中心落在圈内（≤ 0.95r）
   且文本相同」的那个词 → 置 PartText.CalloutDisplay = ①1；列清单时在原位置输出带圈形式
```

`H310A20009.pdf` 实测：页面 4006 条路径 / 4036 条子路径，命中 10 个圆（r = 21px = 1.8mm），
每个圆内正好一个数字，`rMax/rMin = 1.00`、八方位全覆盖——7 个落在 `Part_01`、3 个落在 `Part_02`。
`H310U10004.pdf`（A1，2384×1684pt）的圈半径约 7mm，命中 17 个，全部配上数字。

日志：

```
[CALLOUT] ①1  Part_01.png  圆心(958,213) r=21px=1.8mm  局部(957,213)
[CALLOUT] ⑤5  Part_01.png  圆心(471,462) r=21px=1.8mm  局部(471,462)
[INFO] 圈号标注：10 个圆 / 圈内数字 10 个，归属零件图 10 个
```

输出：每张零件图的记录写进 `parts_info.json` 的 `callouts` 数组，另有一份全局清单 `callouts.txt`
（按零件图分组，零件图以外的圈号单独一节），并在 `parts_text.txt` 每节末尾重复一遍，便于人工核对。

**回填到 `parts_text.txt`（按位置替换，不做字符串替换）**：

圈内那个数字词会被标记（`PartText.CalloutDisplay = ①1`），列清单时在**它原来的位置**输出带圈形式
（默认逐词一行，所以是那一条词记录自己变成 `①1`；`--merge-text-lines` 时则在整句里替换）：

```
改前：  y=1070  x=3051  w=42    h=58   局部(388,531)  1        ← 逐词一行（默认）
改后：  y=1070  x=3051  w=42    h=58   局部(388,531)  ①1

改前：  y=1026  x=3051  w=1306  h=102  局部(388,487)  1 鴨居 G部  ← --merge-text-lines
改后：  y=1026  x=3051  w=1306  h=102  局部(388,487)  ①1 鴨居 G部
```

匹配条件是「词中心到圆心距离 ≤ 0.95 倍半径」且「词文本与圈内数字相同」，尺寸约束与③⑤步一致
（高 ≤ 1.3r、宽 ≤ 1.6r）。所以同一行里若还有尺寸数字（`2`、`20`、`10`），它们**不会**被替换——
实测 `H310A20009.pdf` 的 Part_01 里 `1 5 7 6 8 10 9` 七个数字全部命中，同行其它数字原样保留；
`H310U10004.pdf` 的 17 个圈号同样 17/17 命中（如 `①1 鴨居 G部`、`④4 N部`）。

日志分别给出替换总数与未命中的告警：

```
[INFO] 圈号文字替换：parts_text.txt 中 17 处圈内数字已显示为带圈形式（①1）
[WARN] Part_07.png：圈号 3 个，其中 1 个未在该图的文字中定位到圈内数字（该词可能落在零件框外），未做替换
```

`parts_info.json` 的 `texts` 仍是词级原始文本（`1`），带圈形式只出现在人眼可读的 `parts_text.txt`；
`--no-callout` 时既不识别圈号、也不做任何替换。

**为什么不在像素图上找圆**：二值图上用 Hough / 轮廓圆度找圆也能做，但圈常与引出线相连，
连通域会被引线破坏，需要额外调 `param1/param2`；矢量路径上的圆是"原生数据"，
半径、圆心都是精确值，无需按 DPI 调阈值。代价是：扫描件、文字已转曲的 PDF 没有矢量路径，
本阶段自动跳过（日志 `页面未发现圆形图形` 或 `读取 PDF 矢量路径失败`），不影响分割。

**已知取舍**：只配对 1~3 位纯数字，因此圈内是 `A`、`イ` 或已经带圈的 `⑤`（文字层字符）时不识别；
大孔 / 放大视图若圈里恰好有数字且尺寸比例合适，可能被误认，可调小 `CalloutMaxRadiusMm`，
或用 `--no-callout` 整体关闭。

### 3.11 阶段 11：有线表格内容提取（输出阶段，只读）

`outside_info.json`（3.9）是**从文字坐标反推**表格行列，遇到合并单元格、多列表格会错列。
图纸上的真表格（部品表、型枠表、変更履歴表、表題欄）本身画了框线，直接用框线定行列更可靠：

```
PdfPig ExperimentalAccess.Paths（矢量路径）
   ↓ CollectLineSegments：描边路径的直线段 + 细长实心四边形（CAD 的「粗线」画法）
   ↓                    贝塞尔曲线先扁平化成折线；|dy|≤tol 视为横线、|dx|≤tol 视为竖线
   ↓                    长度 < RuledTableMinLineMm 的短线段丢弃（文字下划线、引线、圆节点）
   ↓ MergeCollinear：共线且间距 ≤ RuledTableLineToleranceMm 的线段接成一条
   ↓ DropStrikeLines：剔除 取り消し線（① 从字身中间横穿且盖住该词 ② 两条相距 <
   ↓                 RuledTableMinCellMm 且夹着同一个词）—— 那不是格子边，是「整行作废」的划线
   ↓ FindCells：对每个「上横线」找最近的「下横线」，再用左右竖线确认四面闭合
   ↓            得到最小闭合矩形（= 单元格）；面积 > 全页 25% 的视为图框
   ↓ DropIsolatedCells：剔掉跟谁都不共边相邻的孤立矩形（文字笔画凑出来的假格子）
   ↓ RemoveContainers：包住别人的「容器格」剔除（多层边框 / 缺线拼出来的大矩形）
   ↓                 顺序不能反：先剔假格子，否则假格子会把包住它的真格子当「套娃」顶掉（整格丢字）
   ↓ Union-Find：共用一条边界（端点在容差内重合）的单元格并成一张表
   ↓ ReadWords + 落格：词中心落在哪个格算哪个格，先给小格挑（最小格优先）
   ↓            合并单元格里的文字自然落在左上角那一格
   ↓ ComposeText：格内按行（纵向中心差 ≤ 0.5 字高）分组、行内按 X 排；间隙 > min(1/4 字高,
   ↓             max(30% 平均字宽, 1/8 字高)) 补空格，换行也补空格（压扁排字才不会被粘成一串）
   ↓            被划线划到的词所在行 = 作废行（IsStruck），不写进 CSV / 二维表
```

**为什么不用 3.9 的推断结果**：3.9 只能给出「行 × 列」的近似（列号是中心 X 聚类），
跨行 / 跨列合并、斜线表头、单元格内换行都会错位；框线是「原生几何」，行列边界就是精确值，
`row_span` / `column_span` 也能如实还原。两者互补：3.9 覆盖没有框线的注记区，3.11 覆盖有线表格。

**为什么要剔除「横穿文字的横线」（`DropStrikeLines`）**：CAD 图里除了格子边，还有 **画在文字上的
划线 —— 取り消し線（删除线）**：某一栏 / 某一行的内容作废了，制图的人就在字上横着画一条（有时两条）线。
它同样是矢量横线，一旦被当成行边界，那一格就被切成几条「比字还矮」的窄带 → 表格凭空多出一行，
文字掉进假行里，同一行的序号 / 图号看起来就错开一行；**而且这一行在图纸上本来就已作废**，
原样输出到 CSV 会被下游当成真数据。所以处理是两件事：先剔除划线本身，再把被划到的行整行剔掉：

```
H310U10004.pdf 表題欄（table_05 第 4 行）：两条相距 1.44mm 的横线从「枠 建て付け注意ラベル貼付要領図」
中间穿过（x=7651~9554，对该行的 4 个词覆盖率都是 100%），把 項目 格切成 34px / 17px / 30px 三段
  修前：行 4 D |（空）| H310U10025 ／ 行 5 （空）| 文字 |（空）／ 行 6 全空
  修后：整个第 4 行剔除（图纸上已划掉作废），CSV 从 18 行变 17 行
```

判据（满足任一即成划线）：

| # | 判据 | 为什么不会误伤真框线 |
| --- | --- | --- |
| ① 单线 | 线的 y 落在某个词**字身中间一半**（上下各让出 1/4），且横向盖住该词宽度 ≥ 60% | 真框线最多擦到字身上下边；下划线只贴字身底下、上划线只压字身顶上，都进不了中间那一半。文字笔画被误当成横线时覆盖率仅 2~4%（`_test/LineProbe` 会打出来），与 100% 差得很远 |
| ② 双线 | 两条横线相距 < `RuledTableMinCellMm`（默认 2mm —— 这么窄的带子装不下字，不可能是行），且都落在同一个词的上下边之内（各留 `RuledTableLineToleranceMm` 余量）、词中心在两条线的公共水平区间内 | 同上是「双线划线」；窄到装不下字，绝不可能是表格的行 |

被划到的词记为 struck，**行内只要有一格被划到 → 整行作废**（划线横着贯穿整行，各列文字高低不同，
可能只有中间几列的字被线穿过）。实测 24 张图纸：只有 `H310U10004` / `H310U10011` / `H310U10018`
三张命中（各 1 行），其余 21 张 0 命中 —— `tables\*.csv` 与修改前逐字节相同。
其中 `H310U10011` / `H310U10018` 的表題欄以前被这两条线切成 4~5 张碎表（`table_04`~`table_08`），
现在还原成 1 张表 + 剔除 1 行作废行。

**为什么某一格会整格丢字（文字笔画凑出来的假格子）**：「最小闭合矩形」的前提是「真格子不会套娃」，
但文字笔画也会凑出矩形 —— `H310U10004.pdf` 表題欄 F 行那段标签里，「要」「図」的几笔正好拼出一个
31×51px 的小方框（x=9023~9054 y=5634~5685），多出一个候选「单元格」。它自己成不了表，却触发了
容器格剔除：F 行中间那格（x=7779~9114 y=5618~5700）包住了这个假格子，被当成「套娃大矩形」删掉 ——
格子一没，落在里面的两个词再没有归属，只能整段消失：

```
修前：F |（空）                                        | H310U10027
修后：F | 枠 ブレーキ部品取付/調整ラベル・注意ラベル貼付要領図 | H310U10027
```

修法是把顺序倒过来：先 `DropIsolatedCells` 剔掉「跟其它候选都不共边相邻的孤立矩形」（它不属于任何
一张表 = 笔画凑出来的），再 `RemoveContainers`。日志会带上剔掉的个数：

```
[INFO] 表格内容：闭合矩形 671 个 → 有效单元格 648 个（已排除图框等超大矩形、文字笔画凑出的假矩形 19 个）…
```

> 副作用（可接受）：假格子不再挡住容器格，个别图纸会多出 1~2 个「文字框」级小表
> （`H310C10031` 的 `table_03`、`H310U10035` 的 `table_01`），表序号随之顺延 —— 这些格里的文字
> 原本也是丢的，现在能取到。24 张图纸实测：`tables\*.csv` 里没有一处文字变少。

**格内文字怎么拼（`ComposeText`）**：按行分组、行内按 X 排；间隙超过
`min(0.25 × 字高, max(0.30 × 平均字宽, 0.125 × 字高))` 就补空格，换行也补空格。
常规排字时字宽 ≈ 字高，起作用的仍是「间隙 > 1/4 字高」；而表題欄长标签、変更履歴窄列是
**压扁排字**（字高不变、字宽约 6 折），只按字高判会把该有的空格吃掉（`枠 ブレーキ部品…` 粘成
`枠ブレーキ部品…`），所以再按本格平均字宽取 30% 判一次 —— 图纸上的间隙比例其实都是 ~0.3 字宽。


**产物**（`RuledTableWriter.cs`，编码约定同其它清单）：

| 文件 | 内容 | 编码 |
| --- | --- | --- |
| `tables_info.json` | 每张表的 `pixel` / `pdf_mm` 坐标、行列数、`struck_row_count` / `visible_row_count`、`rows[].cells[]`（行列号 / 跨度 / 文字 / 词数 / `struck` 标记 / 坐标） | UTF-8 无 BOM |

> 于是「PDF 一格写了三行」就变成「CSV 里多出两条空行、列数错位」。
> 因此写出一律经过 `CsvFile.SingleLine`：CRLF / CR / LF 都压成 `~`（连续换行只留一个，
> 行首行尾的换行丢掉），`tables\*.csv`、`01_アッセンブリ図_部品機能情報.csv`、`02_要領図_部品機能情報.csv`、
> `tables_text.txt` 的二维表与明细共用这条规则（`CsvFile.Escape` 是唯一出口）。
> 读入侧仍兼容老文件：`CsvFile.Read` 会正确解析引号内的换行。

**实测**（`H310U10004.pdf` 第 1 页 @300 DPI）：5 张表 / 604 个单元格 / 555 格有文字。

`D | 枠 建て付け注意ラベル貼付要領図 | H310U10025` 那一行在图纸上被划线作废，整行剔除

**已知取舍**：只认「四面闭环」的格子，所以只有横线的表（表头下一条线）、纯文字对齐凑出来的表
识别不到（这类仍可用 3.9 的 `outside_*`）；表題欄底部「縮尺 / 承認日」等栏位在 CAD 导出时
常是**文字重叠 + 框线未闭合**，会粘成一个大连通格，属预期限制，部品表 / 型枠表不受影响。
划线判据 ① 只认「字身中间一半 + 覆盖率 ≥ 60%」，文字整行溢出到行线上（一格里塞了比行还高的字）
时理论上会被误判成划线 —— 实测 24 张图纸未出现；真遇到时把该窗口丢给 `_test/LineProbe` 看覆盖率，
或调 `RuledTableMinCellMm` 让判据 ② 先不命中。

### 3.12 阶段 14：部品表「下表参照」展开（输出阶段，只读；成品清单 01）

> **执行位置**：`PartSplitterService.Run` 里在 3.14（PDF 信息清单）之后、3.13（品種表摊平）**之前**调用，
> 产物文件名是 `01_アッセンブリ図_部品機能情報.csv`（旧名 `LT_STEP1.csv`；アッセンブリ図 = 組立図，
> 部品機能情報 = 部品表）。它与 3.13 都只读 `tables\*.csv`、各写各的产物，先后顺序不影响内容，
> 调整顺序只是为了固定「先出 `01_…`、最后出 `02_…`」的节奏。
>
> **只有图面分类是 `アッセンブリ図` 的图纸才写**：分类读自 3.14 生成的 `classify\PdfInfoList.txt`
> （清单缺失 / 没有这张图时退回按 `tables\*.csv` 现判，同一套规则）；基本図 / 加工図 / 要領図 / 未识别
> 一律跳过（日志 `… 不是アッセンブリ図，跳过`），并顺手删掉上一次留下的同名产物与改名前的老文件。

**为什么需要**：部品表里常出现 `部品コード = 下表参照` —— 这一行的品番不写在表里，而是
指向紧挨在下面的另一张小表（通常是 `見込み / 部品コード` 两列），表示「按見込み 分几种品番」。
下游 AI 环节按「一个部品一条记录」消费，所以在表格 CSV 落盘之后再补一步展开。

**做法**（`LtStep1Builder.cs`，只读 `tables\*.csv`；除顺手清掉自己改名前的老文件 `LT_STEP1.csv` 外，不改动任何已有产物）：

1. 按文件名顺序遍历 `tables\table_NN.csv`（编号已补零，字典序即图纸上的上下顺序）；
2. 用自带的 RFC 4180 读取器解析（字段内逗号 / 换行、`""` 转义、BOM 自动丢弃，CRLF / LF 都收）；
3. 表头归一化（去掉半角 / 全角空格与换行 —— PDF 里表头常被拆成两行）后，
   **同时含「番号」「部品名」「部品コード」**的表即「部品表（主表）」；
4. 逐条明细看 `部品コード`：不含 `下表参照` 就原样输出；
5. 含 `下表参照` 就**往后**找第一张「表头含 `部品コード` 列、且至少有一条明细」的表当参照表，
   收集它的 `部品コード` 值（跳过空值、重复表头行、以及它自己的 `下表参照`，不接第二层）；
6. 参照表有几条明细，当前行就复制几条，**只替换 `部品コード`**；
   `番号 / 部品名 / 枠区分 / 員数 / 基本寸法 / 切断寸法` 全部沿用原行 —— 同一部品的多个变体共用番号；
7. 找不到参照表 / 参照表没有有效品番 → 该行原样保留 + `[WARN]`，不做猜测；
8. 输出 `01_アッセンブリ図_部品機能情報.csv`（旧名 `LT_STEP1.csv`）：列顺序 = 主表表头，UTF-8 带 BOM、CRLF、RFC 4180
   （转义复用 `RuledTableWriter.EscapeCsv`，与 `tables\*.csv` 完全同款）。

**实测**（`H310U10004.pdf`）：`table_01` 共 12 条明细，其中番号 8「部品セット / 三方枠」
写的是 `下表参照`；下一张 `table_02`（`見込み / 部品コード`）有 2 条 → 这一行拆成 2 条，
`01_アッセンブリ図_部品機能情報.csv` 共 13 条明细（`MZA□968` / `MZA674`）：

```
[INFO] 01_アッセンブリ図_部品機能情報：table_01.csv 第 9 行（下表参照）→ table_02.csv 的 2 条部品コード：MZA□968 / MZA674
[INFO] 01_アッセンブリ図_部品機能情報：1 张主表 → 展开 2 行 → 共 13 条明细，已保存：…\AiAppData\H310U10004\01_アッセンブリ図_部品機能情報.csv
```

**已知取舍**：
- 「下一张表」按**文件序号**判定（图纸上主表在上、参照表在下）；参照表排在主表上方、
  或两者之间夹着别的含 `部品コード` 列的表，就会取错 —— 日志打印「哪张表 → 几条 → 什么值」可核对；
- 参照表的 `見込み`（规格 / 尺寸）列**不进** `01_アッセンブリ図_部品機能情報.csv`：下游按固定列取数，多一列会破坏列约定，
  需要对照时看 `tables\table_NN.csv` 原表；
- 只展开一层（参照表自己写 `下表参照` 时不递归，避免越扯越乱）；
- 没有部品表时不生成文件（只记 `[INFO]`）；`--no-lt-step1`（`BuildLtStep1Table = false`）可关闭；
- 图面分类不是 `アッセンブリ図` 时同样不生成（见 3.14）；`--no-pdf-info-list` 只影响「是否留档清单」，
  不影响这条判定（关掉后退回按 `tables\*.csv` 现判）；
- 改名前的 `LT_STEP1.csv`（`LtStep1Builder.LegacyOutputFileName`）若还在输出目录里，写出前会被删掉，
  避免下游按老名字取到过期内容。

### 3.12.5 要領図一覧（输出阶段，只读；`01_アッセンブリ図_要領図.csv`）

> **执行位置**：`PartSplitterService.Run` 里紧跟 3.12（部品表展开）之后、3.13（品種表摊平）**之前**调用。
> 产物文件名是 `01_アッセンブリ図_要領図.csv`，固定三列 項目 / 要領図漢字 / 図番。
> **只有图面分类是 `アッセンブリ図` 的图纸才写**（分类读自 3.14 生成的 `classify\PdfInfoList.txt`，
> 缺失时退回按 `tables\*.csv` 现判，同一套规则）；别的图类一律跳过并删掉上一次留下的同名产物。
> 代码在 `AssemblyYoryoBuilder.cs`，`--no-assembly-yoryo`（`BuildAssemblyYoryoList = false`）可关闭。

**要解决什么**：組立図上有一张很小的表，列的是「这张組立図用到了哪些要領図」——
1 列 `項目`（`A`、`B`、`F` … 或 `A,M` 这种合写）、1 列要領図名（`要領図漢字`，**多数图纸这列没有标题**）、
1 列 `図番`（10 位）。下游要按「一张組立図 → 它引用的要領図一覧」取数，所以表格 CSV 落盘后顺手抽出来。

**做法**（只读 `tables\*.csv`）：

1. 按文件名顺序遍历 `tables\table_NN.csv`；
2. **表头行同时含「項目」与「図番」**的才是对象文件（两者常隔十几格，但落在表头这一行上），其余表格跳过；
3. `項目` / `図番` 按列名取（归一化后「包含」即命中）；`要領図漢字` ——
   表头写了这个列名就按列名取；没标题（常见）时取 `項目` 与 `図番` 之间**第一条有内容的列**
   （在表头下面 3 行里判断；图纸上它就夹在这两列中间，中间常隔着一两个空格子），
   夹在中间的都空时再整行找第一条有内容的列；
4. 表头下面一行一条，**读到 `図番` 为空或不是 10 位就停** —— 再往下是表題欄、変更履歴表之类的杂行；
5. 多张表按文件名顺序追加到同一个文件；条数为 0 时不生成文件（只记 `[INFO]`）。

### 3.13 阶段 13：品種表摊平（输出阶段，只读；成品清单 02，流水线最后一步）

**要解决什么**：有些表把一个品種的几组部品**横向排开**，同一批列名（`部品コード / 員数`）
在表头里重复出现 N 次，块标题写在列头上方：

```csv
品種,部品名 ： 縦枠上部スペーサー,,部品名 ： 小縦枠上部スペーサー,,部品名 ： 縦枠下部スペーサー,,部品名 ： 小縦枠下部スペーサー,

,,,,,,,,
片引戸,MEACC428,1,MEACC428,2,MEA□□495,3,MEA□□495,4
```

二维表读起来清楚，但下游要的是「一个部品一条记录」，横向并列的 4 组在同一行里，
列名还重复，按列名取数会互相覆盖。于是摊平成固定 4 列的长表，写 `02_要領図_部品機能情報.csv`
（旧名 `LT_STEP2.csv`；要領図 = 要領書，部品機能情報 = 部品表）：

```csv
品種,部品名,部品コード,員数
片引戸,縦枠上部スペーサー,MEACC428,1
片引戸,小縦枠上部スペーサー,MEACC428,2
片引戸,縦枠下部スペーサー,MEA□□495,3
片引戸,小縦枠下部スペーサー,MEA□□495,4
```

**做法**（`LtStep2Builder.cs`，只读 `tables\*.csv`，不改动任何已有产物）：

1. 按文件名顺序（`table_01` … `table_10`，已补零）遍历 `tables\*.csv`；
2. 在前 6 行（`MaxHeaderScanRows`）里找**列名重复**的行：同一列名（归一化后）出现 ≥ 2 次
   —— 这一行就是块的子表头（`部品コード / 員数 / 部品コード / 員数 …`）；
3. 还要在它**及它上方**找到含 `品種` 的单元格作为品種列。两条同时满足才认；
   只满足重复的（型枠表 `A / A員数 / B / B員数 …`、`部品色展開表` 的 4 块）
   因为没有品種列，原样跳过；
4. **块的起点** = 重复次数最多的列名（≥ 2 次）出现的每一列；次数相同时取最左 ——
   块首列是品番（`部品コード`）、右邻是 `員数`，两者重复次数一样，靠左优先正好选中品番列。
   块宽 = 到下一组起点为止（最后一组到表的最右列）；
5. **部品名** = 该块起始列在「子表头行」上方的最后一个非空单元格，去掉 `部品名 ：` 前缀
   （全角 / 半角冒号都认）—— 表头被拆成两行、标题跨列合并都能取到；
6. **明细行**（子表头行之后）：
   - `品種` 为空时沿用上一个非空值（合并单元格在 CSV 里就是留空）；
   - 每块取 `部品コード` 子列的值作品番，`員数` 子列的值作数量；
   - 品番为空的块跳过（该块这一行没有部品）；品番恰好是 `部品コード` 的跳过（表中途重复的表头行）；
7. 每块有品番就出一条 `品種,部品名,部品コード,員数`；多张品種表按文件名顺序**追加**到同一个
   `02_要領図_部品機能情報.csv`，表头只写一次：UTF-8 带 BOM、CRLF、RFC 4180（与 `tables\*.csv` 同一份转义规则，
   见 `CsvFile`）。

**日志**：

```
[INFO] 02_要領図_部品機能情報：table_04.csv 是多列重复的品種表 → 摊平 4 条明细。
[INFO] 02_要領図_部品機能情報：1 张品種表 → 共 4 条明细，已保存：…\AiAppData\<图纸名>\02_要領図_部品機能情報.csv
```

**边界**：

- 块里若还有 `備考` 之类的第三种子列，**不进** `02_要領図_部品機能情報.csv`（下游按固定 4 列取数），
  需要对照时看 `tables\table_NN.csv` 原表；
- 没有「品種 + 列名重复」的表时不生成文件（只记 `[INFO]`）；
  `--no-lt-step2`（`BuildLtStep2Table = false`）可关闭；
- **只有图面分类是 `要領図` 的图纸才写**：分类读自 3.14 生成的 `classify\PdfInfoList.txt`
  （清单缺失 / 没有这张图时退回按 `tables\*.csv` 现判，同一套规则）；基本図 / 加工図 / アッセンブリ図 / 未识别
  一律跳过（日志 `… 不是要領図，跳过`），并顺手删掉上一次留下的同名产物与改名前的老文件 `LT_STEP2.csv`；
- 与 3.12 互不影响：两张产物各自读 `tables\*.csv`，谁缺条件谁不生成。

### 3.14 阶段 15：PDF 信息清单（输出阶段，只读；在 3.12 / 3.13 之前执行）

> **执行位置**：`PartSplitterService.Run` 里紧跟 3.11（有线表格落盘）之后、3.12 / 3.13 之前 ——
> 产物 `classify\PdfInfoList.txt` 是后两者判断「这张图是什么图」的依据（3.12 只对アッセンブリ図写 `01_…`，
> 3.13 只对要領図写 `02_…`）。

**要解决什么**：下游（以及 3.12 的 `01_アッセンブリ図_部品機能情報.csv`、3.13 的
`02_要領図_部品機能情報.csv`）需要先知道「这张图是什么图」。
图面分类在 `drawing_list.csv`（`--list`）里虽然能算，但那是**文件夹级别**的清单，单张分割时手边没有。

**位置**：**整批图纸共用一份**，放在输出根目录下的 `classify\` ——
`<输出根目录>\classify\PdfInfoList.txt`（单张默认 `<图纸目录>\AiAppData\classify\PdfInfoList.txt`，
批量 `<输出根目录>\classify\PdfInfoList.txt`；显式给了输出目录、又没有按图纸名分子文件夹时，
就落在那个目录自己的 `classify\` 里）。**不是**每张图纸各一份。

**做法**（`PdfInfo.cs` 的 `PdfInfoListBuilder`）：

1. 図番号 = PDF 文件名去扩展名；文件名带扩展名；
2. 图面分类：`DrawingListBuilder.Classify` —— 在 `tables\*.csv` 的单元格里找「文件名前 4 位 + 基本図 /
   加工図 / アッセンブリ図 / 要領図」，按优先级命中即定，并记下命中的 `table_NN.csv` 与单元格原文；
   逐格没命中时再按「**同一行**」找一次（`ClassifyByRow`）—— 表題欄常把「図番号」和「図種」写在
   相邻两格里（`H310U10025 | 枠 … 要領図`），那种写法逐格判定找不到；
3. 合并进 `<输出根目录>\classify\PdfInfoList.txt`（UTF-8 带 BOM、CRLF、RFC 4180）：
   同一张图（同 `図番号`）**就地更新那一行**，新图纸追加到末尾 —— 跑完就是一份覆盖全部图纸的总表。

```csv
H310U10004,H310U10004.pdf,アッセンブリ図,table_07.csv：H310U10004 アッセンブリ図

```

**日志**：


### 3.14.1 人工维护：图面分类清单窗口

自动判定本质是「猜」，猜不出来就得让人补。主窗口的「图面分类清单…」（`PdfInfoEditorForm` +
`PdfInfoEditorForm.Designer.cs`）直接编辑 `<输出根目录>\classify\PdfInfoList.txt`：

| 操作 | 说明 |
| --- | --- |
| 直接改「图面分类」格子 | 支持任意写法；改完该行「分类依据」自动记作 `手工设定`（原有依据保留成 `手工设定（原：…）`） |
| 「分类：」下拉 + 「填入选中行」 | 批量给选中行设同一分类，依据同样写 `手工设定` |
| 「判定选中行」/「判定空白行」 | 用该图自己的 `tables\*.csv` 再判一次（`DrawingListBuilder.Classify` → 没命中再 `ClassifyByRow`），命中就填「分类 + 依据」 |
| 「添加行」/「删除行」 | 补漏图 / 清废行；文件名留空、保存时自动补 `図番号.pdf` |
| 「保存」 | `PdfInfoListBuilder.Save`：固定四列、RFC 4180 + BOM + CRLF，与 `Build` 完全同格式；`図番号` 空 / 重复会被拦下 |

**人工值不被覆盖**（关键设计）：`Build` 每次跑都会重算这张图并就地更新那一行 —— 若照旧覆盖，
人工修正跑一次就没了。所以写盘前先过一遍 `KeepManualCategory`：

1. 清单里这一行的「分类依据」以 `手工设定`（`PdfInfoListBuilder.ManualBasisPrefix`）开头 →
   **保留**清单里的分类与依据（日志 `的图面分类是手工设定的（…），保留清单里的值`）；
2. 否则这次自动判定没命中（分类为空）、而清单里已有分类 → 也保留（日志 `这次没判出图面分类，保留清单里上次的值（…）`）；
3. 其余情况（这次判出来了、又不是手工设定）→ 按新结果更新，与以前一致。

> 依据文本在重写时原样搬回：`Save` 用 `ToRow(info, keepBasisWhenUnclassified: true)`，
> 分类暂时空着的行也不会把界面上填的依据丢掉。

**自动判定的目录**：窗口由清单路径反推「输出根目录」（`classify` 的上一层），逐行找
`<根>\<図番号>\tables`，找不到再退 `<根>\tables`（单张、没按图纸名分子文件夹的布局）；
两个都不存在时「判定」按 0 条处理，只能手填。

## 5. 已知边界与局限

1. **不做语义理解，只看几何**：纯文字块（如底部「注）1. □□ 内は別梱包を示す。」这类注记行、
   表題欄 / 変更履歴表残片）只要面积、宽高超过阈值，就会被当成零件输出。
   这类块现由 3.6.1 的「文字行占比 ≥ 60%」规则筛掉（实测 `H310U10004.pdf` 的
   `1419×156`、`2374×158` 两块占比 0.65 / 0.72 → 丢弃，11 张真正的零件图 0.03~0.46 全部保留）；
   该规则依赖 PDF 文字层，扫描件 / 文字已转曲的 PDF 无从判断，此时仍会输出文字块。
2. **不做同名零件去重**：同一零件在图上画了两个视图（如左右两个「戸当り」）时，
   **输出两张**——这是设计意图（每个视图都要单独识别）。
3. **遮蔽方式的适用前提**：块遮蔽（3.3.2，默认）依赖 PDF 文字层——扫描件、文字已转曲的 PDF 取不到词，
   会自动降级为整列遮蔽；整列遮蔽（3.3.4）则要求表格 / 标题栏确实聚在右侧、且与零件区在 X 方向可分。
   两者都不成立时用 `--fixed-mask` 并手工给 `--mask`。
4. **通过引线相连的多个视图会被当成一个零件**：例如 `H310A20009.pdf` 左侧竖排 4 个断面部，
   它们被同一组基准线 / 中心线贯穿，形态学后连成一团，输出为 1 张 `1334×2479` 的图
   （内容是完整的，只是 4 个视图没拆开）。要拆开需要额外的「空白带递归切分（XY-cut）」，
   目前未实现；临时手段是减小 `DilateKernelHeight`（例如 4~6）后重跑。
5. **只处理单页**：多页 PDF 用 `--page <N>` 逐页调用（页码从 0 开始）。
6. **面向线框类图纸**：照片、复杂底纹扫描件、彩色实拍图不在适用范围内。
7. **内存**：A1 @300 DPI 单页峰值约 0.8 GB（见 3.1），请使用 x64 版本并保证可用内存 ≥ 2 GB。
8. **文字坐标依赖 PDF 文字层**（3.8）：扫描件、或文字已转曲（Convert to Outline）的 PDF 取不到文字，
   `texts` 为空；另外以下几种情形会缺字或错位——
   `□` 等以矢量图元绘制的符号（实测「注）1. □□ 内は別梱包を示す。」里的两个方框丢失，
   只剩 `注）1. 内は別梱包を示す。`）、页面 `/Rotate` 旋转或 CropBox 原点偏移
   （日志会打印 `N/M 个词换算后落在画面外` 警告）、文字跨零件框（按 50% 重叠率只归给其中一张）。
9. **分行是启发式**：`parts_text.txt` 的排列顺序按「同一水平线上的词」分组（|纵向中心差| ≤ 0.6 × 字高），
   尺寸数字与引出文字若恰好在同一水平线上，会相邻列出（`1` 和 `2` 挨着）——
   默认逐词一行时每条的框是各自真实的词框，不会互相串位；加 `--merge-text-lines` 拼成一句时
   才会把相邻数字读成 `1 2`。需要机器可读的严格坐标请读 `parts_info.json` 的 `texts`。
10. **表格结构是版面推断，不是真表格**（3.9）：只用文字坐标，不读表格线，也不看单元格边框。
   因此合并单元格（跨行 / 跨列）、斜线表头、单元格内换行会被拆成多个单元格或错列；
   列号只是「中心 X 相近」的聚类序号。需要严格表格语义（合并单元格、跨页续表、单元格合并还原）
   时，请在消费端按 `rows[].cells[].col` 与 `pixel.x` 再做一次归一。
11. **圈号识别依赖矢量路径 + 文字层**（3.10）：扫描件、文字已转曲的 PDF 没有矢量路径，整段跳过；
    圈内若是字母（`A`）、假名（`イ`）或文字层里本身带圈的字符（`⑤`），不会配对；
    圈是「椭圆工具画的椭圆」（宽高比 < 0.90）时也不会被认作圈号。
    大孔 / 放大视图若圈里恰有数字且尺寸比例合适，可能被误认——用 `CalloutMaxRadiusMm` 收紧，或 `--no-callout` 关闭。
    带圈形式（①1）只回填到 `parts_text.txt` 的行文本；`parts_info.json` 的 `texts` 始终是词级原始值，
    且圈号跨在零件框边界（数字词按 50% 重叠率归到框外）时替换不到，日志会给 `[WARN] …未在该图的文字中定位到圈内数字`。
12. **有线表格只认「四面闭环」的格子**（3.11）：只有横线的表、用文字对齐凑出来的表识别不到
    （这类继续用 3.9 的 `outside_*`）；表題欄底部「縮尺 / 承認日」等栏位在 CAD 导出时常是
    文字重叠 + 框线未闭合，会粘成一个大连通格。框线以「描边线 + 细长填充矩形」两种画法识别，
    用色块 / 图案填充表达的分隔线不认；位图 / 扫描件无矢量路径，整段跳过。
13. **「下表参照」按文件序号找参照表**（3.12）：参照表默认排在主表下方（`table_NN` 编号更大）。
    参照表画在主表上方、或主表与参照表之间还夹着别的含 `部品コード` 列的表时，会取错那张表；
    日志会打印「哪张表 → 几条 → 什么值」供核对。参照表自己写 `下表参照` 时不递归展开（只展一层），
    该格原样保留；部品表表头被合并单元格粘成一格（认不出「番号 / 部品名 / 部品コード」）时不生成
    `01_アッセンブリ図_部品機能情報.csv`（旧名 `LT_STEP1.csv`），只记一行 `[INFO]`。另：该文件只带主表原有的列，参照表的
    `見込み`（规格）列不并入 —— 需要对照时看 `tables\table_NN.csv`。
    再另：**图面分类不是 `アッセンブリ図` 的图纸也不生成**（基本図 / 加工図 / 要領図 / 未识别；
    分类来自 3.14 的 `PdfInfoList.txt`），此时会顺手删掉上一次留下的同名产物。
14. **品種表摊平只认「品種 + 列名重复」**（3.13）：表头（前 6 行内）必须既有含 `品種` 的单元格、
    又有同一列名重复出现 ≥ 2 次，缺一条就不生成 `02_要領図_部品機能情報.csv`。所以表头被合并单元格粘成一格、
    或者重复的那几列列名被识别成了不同字样时，该表会被原样跳过（`tables\table_NN.csv` 仍完整）。
    块标题（`部品名 ： …`）必须落在块起始列的正上方；标题跨列偏移时「部品名」会是空串，
    `部品コード` / `員数` 不受影响。块内的第三种列（`備考` 等）不进 `02_要領図_部品機能情報.csv`（固定 4 列约定）。
    另：**图面分类不是 `要領図` 的图纸也不生成**（基本図 / 加工図 / アッセンブリ図 / 未识别；
    分类来自 3.14 的 `PdfInfoList.txt`），此时会顺手删掉上一次留下的同名产物。
15. **PDF 信息清单的图面分类依赖有线表格**（3.14）：`PdfInfoList.txt` 的 `图面分类` 与 `drawing_list.csv`
    同一套规则 —— 要在 `tables\*.csv` 的单元格里同时找到「文件名前 4 位」与四类关键字。表題欄没被识别成
    有线表格、用了 `--no-tables`、或图上图番号写法与文件名不一致时分类留空，
    `01_アッセンブリ図_部品機能情報.csv` / `02_要領図_部品機能情報.csv` 随之都不生成。
    页数 / 大小 / 时间取不到只记 `[WARN]` 并留空，不影响其它产物。

## 6. 案例复盘

### 6.1 同一张图上的两个「戸当り」只切出一个（`H310U10004.pdf`）

**现象**：图纸上左右各画了一个「戸当り」，工具只输出一个。

**诊断**（逐列统计墨迹，打印每列前景像素数）：

| 区域 | X 范围（px，A1@300DPI） | 说明 |
| --- | --- | --- |
| 左侧「戸当り」 | 586 ~ 1022 | 细长竖放零件 |
| 中间剖视图组 | 1868 ~ 4777 | 駒居 / 上レール / フラット下レール / ツバ材 … |
| 右侧视图组 | 5071 ~ 6350 | 4 / A部 / N部 / **戸当り** / 縦枠 / M部 |
| 部品表 + 表題欄 | 7074 ~ | 三张表 + 标题栏 |

**根因**：固定比例 0.50 的遮蔽线在 `X = 4966`，右侧整组视图（含目标「戸当り」）
**全部落在被刷黑的区域里**，从像素层面已经不存在，任何后处理都无法找回。
这与"同名去重""包围盒合并"都无关。

**修复**：引入 3.3.2 的列墨迹自动检测，遮蔽线由 `4966` 移到 `7074`。

**验证数据**（同一 PDF、同一参数）：

| 运行方式 | 遮蔽起点 | 零件数 | 「戸当り」张数 |
| --- | --- | --- | --- |
| `--fixed-mask`（旧行为，比例 0.50） | 4966 | 10 | 1（仅 x=586） |
| 自动遮蔽（新默认） | 7074 | **12** | **2**（x=586 与 x=5914，436×2677 镜像对称） |
| `--mask 0.29 --fixed-mask`（手工对位） | 7046 | 12 | 2 |
| `--mask 0.0`（完全不遮蔽） | 9933 | 21 | 2 + 9 个表格/标题栏垃圾块 |

### 6.2 「一张图被切成一半」（`H310A20009.pdf`）

**现象**：图纸上有 5 个视图（左侧竖排 4 个断面部 + 中部 1 个横向大断面図），
工具只输出 1 张 `683×2461` 的图，右侧一半内容（含中部大断面図）整个不见了。

**版式**（3508×2479）：

| 区域 | X 范围 | Y 范围 |
| --- | --- | --- |
| 左侧 4 个断面部 | 170 ~ 1300 | 0 ~ 2479（竖排） |
| 中部大断面図 | 1400 ~ 3300 | 370 ~ 900 |
| 部品表 + 切断表（右上） | 2400 ~ 3480 | 12 ~ 574 |
| NC95/NC115 型番表（右中） | 2300 ~ 3000 | 2100 ~ 2260 |
| 表題欄（右下 / 左下） | — | 2350 ~ 2479 |

**根因**（两条叠加）：

1. `DetectTableColumnStart` 的列墨迹密实带：x=1618 处 `ink=19 < 阈值 25`，密实带就此断开，
   遮蔽线落在 **1622**。但 1622~3477 这 54% 宽度里，**部品表与中部大断面図在 X 上重叠**，
   于是大断面図右侧 2/3 被涂黑 —— 像素层面已经不存在；
2. 图框（x=26/27、3477/3478；y=9/10、2452/2453）被遮蔽截断成「C 形残片」，
   面积占比从 45% 降到 19%，反而躲过 `MaxBboxFillRatio`，与左侧 4 个断面连成一块，
   输出成「半页图」。

**修复**：3.3.1 图框擦除 + 3.3.2 表格块精确遮蔽（+ 3.3.5 判据）。

**验证数据**（同一 PDF、同一参数 `--debug`）：

| 运行方式 | 遮蔽 | 零件数 | 输出 |
| --- | --- | --- | --- |
| 修复前（整列遮蔽 + 无图框擦除） | X ≥ 1622 全高 | 1 | `Part_01` 683×2461（半页图，中部大断面図丢失） |
| 修复后（块遮蔽 + 图框擦除） | 4 个文字矩形 | **2** | `Part_01` 1334×2479（左侧 4 断面完整）、`Part_02` 1783×866（中部大断面完整） |

回归验证（`H310U10004.pdf`，A1）：图框擦除命中「横 5 / 竖 4」，7 个表格块遮蔽后
丢弃 10 个表格残片，输出 13 张；再经 3.6.1 文字行占比筛除丢掉底部两条表題欄 / 変更履歴表残片
（0.65 / 0.72），最终输出 **11 张**，11 个真实视图全部保留。
